## Scope and baseline

Continue the existing personal-assistant architecture from `f011560b`. Radar observation, notification policy, scoped memory, local history compaction, steering, durable delegation records, and external-effect reconciliation already exist. A separately hosted computer is outside this increment; retain optional provider-neutral computer support.

The source talk is [How Always-On AI Agents Work](https://www.youtube.com/watch?v=DNWDw3bAysc). The complete transcript runs through 45:14. Its middle and final sections add requirements beyond scheduled wakeups: durable step recovery (16:01), interactive thin clients and economical tool selection (18:08–23:31), durable helpers and actionable errors (23:31–27:26), cache-aware context management (27:26–34:41), and regression evaluation across changing models (34:41–45:14).

## Work requirements

1. Match source events to an existing explicitly authorized work item. Persist subscriptions and consumed event identities. Preserve account, owner, source, work-version, and cancellation boundaries. A matching event may resume the agreed objective; it cannot grant new authority or create a new objective. Time-based fallback remains available.
2. Classify work failures before asking for input. Retry a transient dependency failure with persisted bounded backoff. Keep permanent access failures, exhausted allowances, and uncertain external effects visible. Never infer that an ambiguous external action failed and repeat it blindly.
3. Support longer delegated assignments as bounded phases under the original authorization. Preserve intermediate results and reviews. A continuation must not silently create an unlimited budget or bypass a user stop.
4. Verify recovery at individual successful steps, not just job re-publication. Existing effect keys, checkpoints, leases, and persisted events must be reused. Do not mandate Temporal or another workflow service before demonstrating a gap in the existing implementation.
5. Measure context preservation and cache behavior. Stable prompt ordering and compaction already exist. Audit mutable memory placement, tools, summaries, and cache read usage before adding warmup or other provider-specific optimizations.
6. Reuse existing memory, scratchpads, skills, teaching, and regression evaluations. Test changed instructions, source injection, missing evidence, silent waits, genuine blockers, and completion on an extended lifecycle. A model's completion claim is not acceptance evidence.

## Response requirements

The [official Intelligent UI announcement](https://openai.com/index/gpt-6-for-everyone/) describes native streamable components, a compiler processing output during generation, and model choice of content, layout, visuals, and interaction. The [Help Center guide](https://help.openai.com/en/articles/20001598-intelligent-ui-in-chatgpt) describes buttons, forms, charts, interactive experiences, and optional persistence of component state.

Existing weather and email-draft widgets are useful primitives, but do not satisfy general response composition. The implementation must support mixed prose and composed layouts; progressively available content; comparisons, charts, diagrams, forms, checklists, and calculations; meaningful local interaction; persisted state; accessible controls; and plain-text degradation where a client cannot render a component. The model must also choose ordinary prose when that is sufficient.

Research reusable open-source streaming/schema packages before selecting the protocol. Keep the backend authoritative for validation, authorization, external actions, and state. Native iOS remains UIKit. Web/Electron and retained Android must implement the shared contract or have an explicit safe fallback. Never execute arbitrary generated host code to render a response.

- Work can subscribe to a specific owned connected account's thread, item, sender, or event kind. Committed observations wake it regardless of notification disposition. - Terminal failures are classified. Transient dependency failures receive bounded persisted backoff and reuse the original run and completed effect keys. - The shared response vocabulary covers composed layouts, prose, metrics, comparisons, charts, diagrams, controls, checklists, timelines, and local arithmetic. - The response compiler preserves streaming prose and renders validated components incrementally inside an explicit UI fence. Incomplete or invalid compositions become safe text. Generated HTML, script, arbitrary host calls, prototype paths, cycles, oversized documents, undeclared state writes, and invalid input ranges are rejected. Arithmetic is declarative. - Context preparation and provider usage events share an attempt identity. They record UTF-8 sizes, instruction and tool fingerprints, the prefix before known mutable sections, history/summary/image counts, and reported cache reads. Payloads contain no prompt content, tool arguments, image data, or credentials. Missing provider cache accounting stays unknown rather than appearing as a cache miss. Memory index ordering is deterministic, and memory/scratchpad blocks follow fixed policy. These measurements describe the executor request; provider translation can still affect the actual cached prefix.
- Delegated assignments can use two or three explicit phases under the existing eight-run allowance and original deadline. Each intermediate result and verified review are preserved before a transactional continuation queues the next phase. Lost publication uses the existing queued-run reconciler. Phase identities fence stale reviews and late results. Rework retains the originating assignment, required sources, plan, budget, and deadline. A partial result or blocker does not finish or advance the assignment; a bare review completion claim receives only the existing bounded review retry.
- Phased plans retain owner, Space, originating user message/run, optional work version, and bot instruction fingerprints. Background work runs recover the authorizing message from the owned, version-matched work record. These boundaries are checked before the model, tools, effect claims after a slow approval review, and phase continuation. Cancellation, deleted source authorization, changed instructions, paused work, or a changed work version prevent further phases. Earlier completed runs do not hide cancellation of the current phase.
